# trae-agent — T1 review

Subject: `/data/samples/agents/trae-agent` (origin https://github.com/bytedance/trae-agent, MIT, Python package `trae_agent`, pyproject). ByteDance's open-source research CLI agent for SWE tasks — the sibling scaffold behind the Trae IDE line and the SWE-bench-Live / Multi-SWE-bench eval efforts. This is the upstream itself (census `upstream_remote` == `origin`), not a fork.

## Anchor question

**Which anchor subject is this closer to, and why?** crush (69.0) — it shares crush's "small honest single loop + tool layer" shape and CI-backed tests, but trae-agent lacks crush's permission service, loop detection, resume, and LSP/MCP depth, landing it well below crush and a full story-breadth below the C-anchor nanocoder; clearly above codel because a real, partly-tested loop exists (`base_agent.py:163`).

## Per-dimension scores

### architecture — 6/10 (weight 15)
Clean layering for a small codebase: `agent/` (BaseAgent loop + TraeAgent specialization), `tools/` (registry + Tool/ToolCall/ToolExecutor base), `utils/llm_clients/` (per-provider clients behind an LLMClient match-factory), `prompt/`. Loop is a legible bounded while: `base_agent.py:163-176`, per-step split into `_run_llm_step` / `_finalize_step` (`base_agent.py:204-238`), tool fan-out parallel-or-sequential (`base_agent.py:337-341`). No god files — max file is `cli.py` 731 LOC (which does mix arg parsing, Docker preflight `cli.py:53-66`, and pyinstaller tool builds `cli.py:101-115`). Two structural costs keep it at 6, not 7: (1) the conversation state model is split — the loop passes only *new* messages each step (`base_agent.py:166`) while real history accumulates inside the LLM client (`openai_compatible_base.py:120` `self.message_history = self.message_history + parsed_messages`), so history is invisible to the loop and unmanageable from it (recent fix `e839e55` "persist tool outputs in message history" shows this seam was broken until recently); (2) `BaseAgent.__init__` fuses executor wiring, Docker wiring, and CKG cache clearing (`base_agent.py:44-85`). Above nanocoder-5 (no UI coupling, no parallel loop re-implementations); below crush-7 (no policy/state services, thinner seams).

### verification — 5/10 (weight 15)
80 test methods / ~1.7k LOC (`tests/`, 8 files): tools are behavior-tested (`test_bash_tool.py` session/timeout semantics, `test_edit_tool.py`, `test_json_edit_tool.py`), config resolution tested (`test_config.py` 11 methods), provider message-shaping tested with fakes (`test_google_client.py`, `test_openrouter_client_utils.py`), CLI arg validation tested (`test_cli.py:18-145`). CI runs pre-commit (ruff/pyright) + pytest on every push/PR (`unit-test.yml:2-5,33-34`, `pre-commit.yml:2-5`). Docked hard for: the agent loop itself has **zero** tests — `execute_task`/`_run_llm_step` appear in no test file (grep of `tests/` for `execute_task`: no hits); `test_trae_agent.py` only covers `new_task`, git-diff, patch filtering, completion detection, and property access. And CI deliberately skips the network-provider suites (`Makefile:42` `SKIP_OLLAMA_TEST=true SKIP_OPENROUTER_TEST=true SKIP_GOOGLE_TEST=true`). The repo *ships* a serious eval harness (SWE-bench / SWE-bench-Live / Multi-SWE-bench, `evaluation/README.md`) but it never runs in CI. No fuzzing. Below the 6-rung "standard design, tested" because the tested parts are satellites, not the loop; above crush-7 obviously not.

### safety-enforcement — 3/10 (weight 10)
Nothing binds by default. There is no approval concept anywhere in the package (grep for `approv|permission|confirm|allowlist|deny` hits only Docker daemon-permission error strings, `cli.py:78,398`); `bash` spawns arbitrary commands straight on the host (`bash_tool.py:41-59`, sentinel-based `_BashSession.run` ~:110-130) and is a *default* tool (`trae_agent.py:21-27`). The only isolation is opt-in whole-environment Docker delegation (`--docker-image|container-id|dockerfile|image-file`, `cli.py:146-259`, `docker_manager.py`), which is real isolation but coarse and off by default. It also leaks: only three tools are routed into the container — `docker_tools=["bash", "str_replace_based_edit_tool", "json_edit_tool"]` (`base_agent.py:68`) — so in "sandbox" mode MCP tools (arbitrary stdio servers) and ckg still execute on the host (`docker_tool_executor.py:55-66` routing). No denylist, no egress control, no project trust. Between codel-2 (policy-is-prompt-text, misleading) and nanocoder-5 (real jail + fail-open): trae has real-but-opt-in jail machinery and zero in-loop enforcement, and the docs never claim safety it lacks — 3.

### token-economy — 2/10 (weight 10)
No compaction, no context-window awareness, no cache discipline. Conversation history grows unbounded inside the client (`openai_compatible_base.py:119-123`); nothing measures projected context. What exists: tool-output truncation at 16,000 chars with a re-search-the-file notice (`run.py:17-26`, applied in `edit_tool.py:300`, `edit_tool_cli.py:42`), per-request `max_tokens` (`config.py:48-62`), and cumulative token/cost accounting for reporting only (`base_agent.py:281-288`). On overflow the run doesn't degrade: the retry decorator blindly re-attempts the doomed request with random 3-30s sleeps (`retry_utils.py:38-50`) and then aborts the run (`base_agent.py:177-180`). One notch above codel-1 only because tool-output clipping is a real (if standard) mechanism; codel at least notices total prompt size.

### orchestration — 3/10 (weight 10)
Single agent, single task, `max_steps` cap with error-abort-and-break (`base_agent.py:163-177`). No subagents, no queues, no resume/continuation, no budgets. Crash posture: tool-close and MCP cleanup in `finally` (`base_agent.py:182-196`), Docker teardown unless `--docker-keep` — decent resource hygiene, no state recovery. Batch parallelism exists only in the eval harness (`ThreadPoolExecutor`, `evaluation/run_evaluation.py:315,450`), not the product. Below codel-4 (which at least has a restart-tolerant DB task queue); the floor-4 territory belongs to designs that persist work, which this does not.

### interop — 4/10 (weight 10)
MCP client with an explicit opt-in allowlist (`allow_mcp_servers`, `trae_agent.py:55-56,75-77`) — stdio transport only; HTTP and WebSocket configs raise `NotImplementedError` (`mcp_client.py:47-50`). Broad model interop instead: 7 providers (OpenAI, Anthropic, Azure, OpenRouter, Doubao, Ollama, Google; `llm_client.py:11-42`) plus user-registered custom OpenAI-compatible endpoints via `base_url`+`api_key` (`config.py:84-95`), and the `OpenAICompatibleClient`/`ProviderConfig` base makes new compatible providers cheap (`openai_compatible_base.py:34-66`). Headless-ish: `trae-cli run` is scriptable and emits per-run trajectory JSON, but there is no documented machine-output contract (no `--json` event stream), no SDK (SDK is roadmap prose, `docs/roadmap.md:5-21`), no MCP server, no ACP, no IDE surface. One above SWE-agent's 3 for MCP + provider breadth.

### operability — 4/10 (weight 10)
Post-hoc observability is the strongest suit: every run can dump a full structured trajectory (steps, LLM messages, tool calls/results, usage; `trajectory_recorder.py:20-263`) and LakeView renders it into a tagged step digest (`docs/TRAJECTORY_RECORDING.md`, `lake_view.py`). Interactive REPL mode (`trae-cli interactive`). Config is tidy: YAML/JSON with legacy shim (`config.py`, `legacy_config.py`), env-var key resolution (`config.py:96-116`). But there is no resume, no rewind/checkpoint, no session store — a dead run is re-run from zero; blocking sleeps in retry (`retry_utils.py:44-50`) stall the async loop; provider errors surface as print+traceback from the decorator. Docker lifecycle UX (attach/build/tar-load/keep) is genuinely convenient (`cli.py:242-266`, `docker_manager.py:47-66`). No SECURITY.md.

### originality — 6/10 (weight 10)
Verified in code, not marketing: (1) **LakeView** — post-hoc LLM step extraction with a fixed 8-tag taxonomy (WRITE_TEST/VERIFY_TEST/EXAMINE_CODE/WRITE_FIX/VERIFY_FIX/REPORT/THINK/OUTLIER) over recorded trajectories, two-prompt extractor+tagger design (`lake_view.py:16-56`, invoked `:101,153`) — a trajectory-analysis idea no other corpus subject has; (2) **patch-selection research harness** — a separate sandboxed selector agent that adjudicates N candidate patches with grouping and majority voting (`evaluation/patch_selection/selector.py:22-36`, `trae_selector/selector_agent.py`); (3) **tool transplant into Docker** — pyinstaller-frozen edit/json-edit tools copied into the container at `CONTAINER_TOOLS_PATH` with host↔container path translation (`cli.py:101-115`, `docker_manager.py:19`, `docker_tool_executor.py:33-46`). Docked because the agent core itself is vanilla and the tool set is honestly attributed porting from Anthropic quickstarts + one Apache-2.0 aider function (`bash_tool.py:1-9`, `trae_agent.py:187-193`).

### durability — 6/10 (weight 5)
Real institutional backing: bytedance org repo, MIT, 12.1k stars, homepage linked to the Trae product line, CI with `if: github.repository == 'bytedance/trae-agent'` gating (forks don't burn CI), CONTRIBUTING, pre-commit. Counterweight: remote `pushed_at 2026-02-05` is ~8 months quiet at review and 235 open issues — the census shallow-clone numbers (1 contributor) are artifacts, but the remote signal says slow, not dead. No SECURITY.md, single-workflow-pair CI. Same rung as SWE-agent's 6: strong sponsor, research-cadence maintenance.

### docs-dx — 5/10 (weight 5)
README covers install (uv), YAML config, per-provider runnable examples (`README.md:142-162`), Docker-mode recipes (`:181-196`), trajectory/lakeview flags. Four in-repo docs: tools, trajectory recording, legacy config, roadmap (`docs/`). Error messages are user-facing (rich console; Docker daemon guidance `cli.py:398`). Docked vs the 7-rung: no SECURITY.md, no session/config reference beyond README, provider quirks (e.g., `should_use_max_completion_tokens`, `config.py:58`) undocumented, roadmap oversells ("comprehensive SDK") against a codebase with no programmatic API (`docs/roadmap.md:5-21`).

## Strongest / weakest

- **Strongest dimension: architecture** (6, tied on raw number with originality/durability but carrying the 15-weight lane): the small codebase keeps loop/tools/providers genuinely separated — everything else is built on that frame.
- **Weakest dimension: token-economy** (2): unbounded client-side history with no compaction, overflow handled by blind retry then crash.
